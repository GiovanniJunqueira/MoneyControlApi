# Contexto do projeto — Financeiro API

Backend do sistema de controle financeiro pessoal. O usuário organiza os dados em **abas** (`Tab`, ex: uma por banco) — cada aba tem seus próprios **Gastos** e **Devedores**, módulos independentes entre si. Este arquivo existe pra dar contexto rápido ao Claude Code sobre decisões já tomadas — evita re-perguntar coisas já definidas.

## Stack e por quê

- **Java 17 + Spring Boot 3** (Web, Data JPA, Security, Validation) — escolhido deliberadamente ao invés de Node.js porque é o que mais aparece em vagas do mercado (decisão do usuário).
- **PostgreSQL** via Spring Data JPA. Schema versionado com **Flyway** (`src/main/resources/db/migration`), `ddl-auto: validate` — não usa mais `update`.
- **JWT stateless** (biblioteca `jjwt`) para autenticação — multiusuário, cada um só vê seus próprios dados.
- **Maven**, sem Maven Wrapper incluso no pacote (gerar com `mvn -N wrapper:wrapper` se quiser). Existe um `Dockerfile` multi-stage pra build/execução em container, usado no deploy.
- **Deploy**: API no ar em https://financeiro-api-bc70.onrender.com (Render, free web service, via `render.yaml`), banco no **Neon** (Postgres free serverless), frontend planejado pro **Vercel**. Config sensível (DB, JWT secret, CORS, porta) é 100% via variáveis de ambiente — ver tabela no `README.md`.

## Decisões de produto (não óbvias pelo código)

1. **Multiusuário desde o início** — cada `User` tem suas próprias `Tab`s, e cada `Tab` tem seus próprios `Category`, `Expense`, `Debtor`, `Debt`, `ModuleSettings`. Toda query filtra por `tabId` (listagem) ou `userId` do JWT (ownership check em update/delete, via `CurrentUser.id()`) — ver seção "Abas" abaixo.
2. **Módulos Gastos e Devedores são totalmente independentes** — um gasto NÃO gera dívida automaticamente pra ninguém. Foi uma decisão explícita do usuário (perguntei e ele confirmou que quer os dois desacoplados).
3. **Cada módulo tem seu próprio "período fiscal"** (dia de fechamento do mês, configurável de 1 a 28, default 1) — independente por módulo **e por aba**. Duas abas podem ter dias de fechamento diferentes entre si, e dentro da mesma aba Gastos e Devedores também são independentes.
4. **Dívidas têm status com 3 estados**: `pendente` → `parcial` → `quitado`, recalculado automaticamente toda vez que um `DebtPayment` é registrado (soma pagamentos vs. valor total da dívida). Ver `DebtService.registerPayment()`.
5. **Categorias são 100% customizáveis pelo usuário** (nome, cor, ícone) — não existem categorias fixas/seed, mas são únicas por aba (duas abas podem ter cada uma sua própria categoria "Mercado").

## Abas (`Tab`) — multi-workspace

Adicionado depois do MVP inicial (o usuário queria separar os dados por banco/conta, ex: BTG vs Itaú, com uma visão consolidada). Pontos importantes:

- Toda conta nova ganha automaticamente uma aba **"Geral"** no registro (`AuthService.register()`). A migração `V2__add_tabs.sql` fez o mesmo retroativamente pra usuários que já existiam antes desse recurso — todos os dados antigos foram parar numa aba "Geral".
- `Category`/`Expense`/`Debtor`/`Debt`/`ModuleSettings` têm **os dois** campos `user` (redundante, mantido só pro ownership check em update/delete continuar simples) e `tab` (o campo que realmente importa pra listar/filtrar). Ver `findOwnedTab()` em cada Service.
- Excluir uma aba (`TabService.delete`) faz cascade no banco (`ON DELETE CASCADE` nas FKs de `tab_id`) — não tem lógica de limpeza manual. Bloqueado se for a última aba do usuário. A migration `V2` também corrigiu de passagem um bug preexistente: a FK `debt_payments.debt_id` não tinha cascade, então excluir uma dívida com pagamento registrado quebrava com violação de FK.
- `GET /dashboard/visao-geral` soma os dados de **todas** as abas do usuário — implementado como um loop em `DashboardService.visaoGeral()` que chama a mesma lógica por-aba (`gastosParaAba`/`devedoresParaAba`) pra cada `Tab` e funde os resultados. Categorias/pessoas com o mesmo **nome** em abas diferentes são somadas numa linha só (decisão do usuário).
- **Pegadinha de período na Visão Geral**: como cada aba pode ter um `closingDay` diferente, não dá pra deixar cada aba resolver seu próprio "período atual" de forma independente (duas abas podem discordar sobre qual é o mês corrente num dia de transição). A solução foi fixar uma única `period key` (formato `"YYYY-MM"`) ANTES do loop e passar a mesma pra `ExpenseService.resolvePeriod(key, closingDayDaAba)` de cada aba — cada uma calcula sua própria janela de datas a partir da mesma chave. Quando não vem `period` explícito na query, essa chave é calculada com `FiscalPeriodCalculator.getCurrentFiscalPeriod(1)` (closingDay=1 fixo como referência, não `YearMonth.now()` puro) — já teve um bug aqui onde usar o mês de calendário puro descolava do período que as telas por-aba mostravam por padrão.

## Reset de senha ("esqueci minha senha") — primeiro e-mail que esse app manda

Até essa feature, o backend nunca tinha enviado e-mail nenhum (sem dependência de mail, sem SMTP configurado). Fluxo padrão de dois passos, tudo em `AuthService`:

- **`POST /auth/forgot-password`** (`ForgotPasswordRequest{email}`, público): se o e-mail existe, gera um token (`UUID.randomUUID()`), grava em `users.reset_token`/`reset_token_expires_at` (válido 1h, migration `V15__password_reset.sql` — índice único **parcial**, `WHERE reset_token IS NOT NULL`, pra permitir múltiplos usuários com token `NULL` ao mesmo tempo) e manda o link (`{FRONTEND_URL}/reset-password?token=...`) por e-mail via `MailService`. **Sempre responde `204`, exista ou não o e-mail** — decisão de segurança deliberada, pra não deixar alguém descobrir quais e-mails têm conta só tentando resetar a senha deles. Um novo pedido sobrescreve qualquer token anterior (só um reset pendente por vez).
- **`POST /auth/reset-password`** (`ResetPasswordRequest{token, newPassword}`, público): acha o usuário pelo token, valida que não expirou, troca a senha (`passwordEncoder.encode`) e **limpa o token** (não reutilizável). Token inválido/expirado → `400`.
- **`MailService`** (Gmail SMTP via `spring-boot-starter-mail`, `spring.mail.*` em `application.yml`) — **engole qualquer `MailException` e só loga** (não propaga pro chamador), porque `forgotPassword()` já responde sucesso genérico antes de saber se o envio deu certo; se o SMTP estiver mal configurado, a falha fica só no log do Render, sem quebrar a resposta pro usuário nem vazar informação.
- **Variáveis novas**: `MAIL_USERNAME`/`MAIL_PASSWORD` (conta Gmail + [senha de app](https://myaccount.google.com/apppasswords), não a senha normal da conta) e `FRONTEND_URL` (pra montar o link do e-mail) — sem elas configuradas no Render, o endpoint continua respondendo `204` normalmente, só o e-mail não sai (fica no log como erro).
- Os dois endpoints entraram no `permitAll()` do `SecurityConfig` ao lado de `/auth/register`/`/auth/login`.

## Gastos recorrentes e dívidas parceladas

Pedido do usuário: "se o thiago me deve 2000 e vai pagar em 5x, aí apareça durante os meses quanto ele me deve" (dívida) e um gasto recorrente onde ele informa "quanto é, período e valor mensal". A decisão de design (não óbvia): **não existe nenhuma tabela de "template" nem projeção calculada em tempo de leitura** — tanto a recorrência de gasto quanto o parcelamento de dívida **materializam N linhas reais de uma vez, na hora de criar**, ligadas entre si por um id de grupo. Isso significa que **todo** o resto do sistema (filtro por período fiscal, dashboard, soma por categoria, `totalDevido` do devedor) continua funcionando sem nenhuma mudança — cada ocorrência/parcela é só mais uma linha normal com sua própria `date`, exatamente como já era.

- **`Expense.recurringGroupId`** (nullable) liga as ocorrências de um gasto recorrente. `ExpenseRequest.recurrence`: `null`/`"NONE"` = avulso (comportamento de sempre); `"FIXED"` + `recurrenceMonths` = cria exatamente esse tanto de `Expense`, uma por mês a partir de `date`; `"INDEFINITE"` = cria `INDEFINITE_HORIZON_MONTHS` (24, constante em `ExpenseService`) meses de uma vez. **Não existe recorrência infinita de verdade** — "indefinido" só materializa um horizonte grande o suficiente pra parecer sem fim; se a pessoa passar desse prazo, precisa cadastrar de novo (nenhum job de background fica gerando mais linhas). Category/amount/description são idênticos em todas as ocorrências geradas.
- **`Debt.installmentGroupId` + `installmentNumber` + `installmentTotal`** (todos nullable) fazem o mesmo pra dívidas parceladas. `DebtRequest.amount` quando `installments > 1` é o **valor TOTAL**, dividido em `installments` parcelas mensais a partir de `date` — a divisão usa `RoundingMode.DOWN` em cada parcela e joga a diferença de arredondamento inteira na **última** parcela, garantindo que a soma bate exatamente com o total pedido (ex: R$1000 em 3x vira 333,33 + 333,33 + 333,34). Cada parcela é uma `Debt` normal, com seu próprio `status`/`paidAmount`/`DebtPayment`s — pagar ou quitar uma parcela não afeta as outras.
- **Editar/excluir com `applyToFuture`**: `ExpenseUpdateRequest`/`DebtUpdateRequest` ganharam um `boolean applyToFuture`. Quando `true` e a ocorrência pertence a um grupo, a mudança de categoria/valor/descrição (gasto) ou valor/motivo (dívida) é aplicada a ela **e a todas as ocorrências com `date >= a desta`** do mesmo grupo — a `date` de cada uma continua a que já tinha (só quando `applyToFuture=false` a data da própria ocorrência pode mudar). O DELETE aceita `applyToFuture` como query param com o mesmo efeito, mas excluindo em vez de editar.
- **Cuidado com `open-in-view: false` aqui**: `ExpenseService.update()`/`create()`/`delete()` e `DebtService.update()`/`create()`/`delete()` precisaram ganhar `@Transactional` por causa disso — sem a anotação, `findOwned(id)` e a query de "achar as ocorrências futuras do grupo" rodavam em transações/sessões separadas (cada chamada de repository sem transação externa abre e fecha a sua), então o objeto `expense`/`debt` original ficava com os campos desatualizados (as mudanças só foram aplicadas nos objetos retornados pela SEGUNDA query, não nesse) e, no caso do `Expense` (que expõe `category` no DTO de resposta, um `@ManyToOne` lazy), a chamada `expense.getCategory()` em `toResponse()` **quebrava com `LazyInitializationException`** fora de uma sessão aberta — isso realmente aconteceu no teste manual (`update` com `applyToFuture=true` retornava 500, mas o `UPDATE` já tinha sido salvo certinho no banco). Com `@Transactional`, a mesma entidade fica no *identity map* do Hibernate entre as duas queries dentro do método inteiro, então tanto o objeto original quanto os da lista de "ocorrências futuras" acabam sendo a mesma instância gerenciada — resolve os dois problemas de uma vez. `create()` também ganhou `@Transactional` só por atomicidade (criar N linhas em loop, cada `save()` sem transação externa commitava uma de cada vez — se a N-ésima falhasse, ficariam parcelas/ocorrências órfãs no banco).
- **Frontend**: `EditExpenseModal`/`EditDebtModal` (novos, ao lado dos `AddExpenseModal`/`AddDebtModal` que só criavam) mostram o checkbox "Aplicar às futuras também" **apenas** quando a ocorrência tem `recurringGroupId`/`installmentGroupId`. `ConfirmDeleteRecurringModal` (compartilhado pelas duas telas) pergunta "excluir só essa" vs. "essa e as futuras" ao excluir uma ocorrência que pertence a um grupo — se não pertence a nenhum grupo, exclui direto sem perguntar (comportamento de sempre).

## Módulo Bets (banca de apostas) — completamente separado das abas

Adicionado a pedido do usuário como uma segunda "aplicação" dentro do mesmo backend/frontend, sem nenhuma relação com `Tab`/Gastos/Devedores. Só aparece pra quem tem `User.betsEnabled = true` (toggle em `PUT /auth/settings`), mas as tabelas e endpoints existem pra todo mundo — a checagem de visibilidade é só no frontend (`BetsLayout` redireciona pra `/` se `betsEnabled` for `false`).

- **Modelo**: `bet_houses` (casas de aposta do usuário, com `position` pra ordem definida por drag-and-drop), `bet_months` (um "mês" de acompanhamento, alinhado a um mês de **calendário** — ver abaixo), `bet_unit_value_changes` (log append-only do valor da unidade ao longo do tempo), `bet_daily_balances` (uma entrada de saldo por casa por dia, unique `(house_id, date)`, com `balance` = saldo final e `opening_balance` opcional = ajuste manual do saldo inicial) e `bet_month_starting_balances` (snapshot do saldo de cada casa no instante em que o mês começou).
- **Mês = mês de calendário escolhido pelo usuário, não "hoje até eu clicar de novo"**: `POST /bets/months` recebe `year`/`month` (não usa mais `LocalDate.now()` como início) — `startMonth()` sempre usa o dia 1 daquele mês como `startDate`. Três casos, todos tratados em `startMonth()`:
  - **Mês atual ou futuro**: fecha o mês aberto existente (se tiver) e abre o escolhido como o novo mês corrente (`endDate = null`) — mesmo fluxo de sempre, só que agora `startDate` é sempre dia 1, não o dia em que a pessoa clicou. Um mês *futuro* (ainda não chegou no calendário) já pode ser criado e vira o mês corrente na hora — só mostra o dia 1 até o calendário alcançá-lo (ver `resolveRangeEnd`).
  - **Mês totalmente no passado** (ex: registrar agosto estando em setembro, pra backfill): **não mexe** no mês aberto atual — nasce **já fechado** (`endDate` = último dia daquele mês) e convive como um registro histórico à parte. `startingBanca` usa o saldo **atual de verdade** das casas (mesma lógica de sempre, sem caso especial) — decisão explícita do usuário, mesmo sabendo que esse número não reflete o saldo real da época; ele corrige manualmente o dia 1 via o saldo inicial editável se quiser.
  - O mês de backfill entra normalmente na conta do "lucro total" do topo (ver `profitLoss`/`overview()` abaixo) — não fica isolado.
- **Painel em funil (mês → dia → casa)**: `GET /bets/months` lista o resumo de cada mês; `GET /bets/months/{id}/days` calcula, **em memória, dia a dia**, o saldo de cada casa por carry-forward e o resultado, sem nada disso ser armazenado — só `bet_daily_balances`/`bet_month_starting_balances` existem fisicamente. Os dois reaproveitam o mesmo método privado `computeMonthDays()` (chamado por `listMonthDays()` e, um mês de cada vez, por `listMonthsHistory()`) — **não existe mais** um valor de "banca final" guardado ou inferido do próximo mês; tudo é recalculado na hora, o que também é o que permite editar um mês **fechado** sem deixar nada obsoleto.
- **Intervalo de dias mostrado** (`resolveRangeEnd`): mês já fechado → do início até o fim de verdade. Mês futuro (calendário ainda não chegou) → só o dia 1, como placeholder. Mês corrente em andamento → do início até **hoje + 1** (sempre um dia a mais pronto pra preencher amanhã), sem passar do último dia real daquele mês.
- **Editar um dia é permitido em QUALQUER mês** (aberto ou já fechado, inclusive um de backfill) — `POST /bets/months/{monthId}/houses/{houseId}/balance` (a rota leva o `monthId`, não infere mais "o mês aberto"). Validação: a data tem que estar dentro do próprio intervalo de dias reais desse mês e nunca no futuro (`min(hoje, último dia do mês)`). Isso só é seguro porque nada mais depende de um valor "congelado" de banca final (ver ponto anterior) — antes disso, editar mês fechado deixava o mês seguinte com número errado.
- **`profitLoss`/`profitLossUnits` do mês = SOMA do resultado de todas as casas** (mesma fonte do `houseSummaries`, que é literalmente o mesmo acumulador exposto por casa) — **não** `endingBanca − startingBanca`. Isso foi uma correção explícita: as duas contas coincidem na maioria dos casos, mas divergiam sempre que existia um ajuste de saldo inicial (depósito/saque) no mês, porque a banca real muda mas o "resultado de aposta" não deveria — o usuário confirmou que quer os dois **sempre** iguais, com o resultado sendo a fonte de verdade. `endingBanca` continua sendo calculada (banca real, `days.get(0).total()`) e devolvida na resposta, só não alimenta mais `profitLoss`.
- **`overview()` = SOMA do `profitLoss` de cada mês** (chama `computeMonthDays()` uma vez por mês, igual `listMonthsHistory()`) — trocou a lógica anterior (telescopar da banca atual menos a `startingBanca` do mês mais antigo por `createdAt`), que gerava um número diferente da soma simples dos meses exibidos na lista logo abaixo. Pedido explícito do usuário: "o saldo geral de todos os meses tem que somar os meses".
- **`houseSummaries` (resumo por casa do mês inteiro)**: `computeMonthDays()` já varre dia a dia calculando o `result`/`resultUnits` de cada casa — o resumo é só um acumulador (`Map<UUID, BigDecimal>` com `.merge(id, result, BigDecimal::add)`) somado ao longo do mesmo loop, sem nenhuma query extra, positivos e negativos normalmente (`BigDecimal.add`).
- **Saldo inicial do dia editável (`bet_daily_balances.opening_balance`)**: por padrão o "início do dia" de uma casa é sempre o saldo final do dia anterior (carry-forward automático, recalculado a cada leitura — `opening_balance = NULL`). A pessoa pode sobrescrever esse valor manualmente, pra registrar um depósito/saque na casa sem que a diferença conte como resultado de aposta (`resultado = final − início`, e se os dois baterem o resultado fica 0). **Cuidado no frontend**: não dá pra decidir "a pessoa mexeu no campo?" por um booleano de `onChange` (frágil, já causou o campo "perder" o valor calculado sem motivo aparente) — em vez disso, `UpdateBetBalanceModal` compara o valor **submetido** com o valor que foi mostrado como padrão (`Math.abs(diff) < 0.005`).
  - **Bug já corrigido**: quando o campo não mudava, o modal sempre mandava `null` — o que APAGAVA um ajuste explícito já salvo (ex: editar só o "saldo final" de um dia que já tinha "saldo inicial" ajustado por um saque/depósito zerava esse ajuste, porque a comparação só olhava o valor mostrado, sem saber se ele vinha de um ajuste explícito ou do carry-forward automático). Corrigido expondo o valor bruto salvo em `BetMonthDayHouseResponse.openingOverride` (null = automático, valor = ajuste explícito) — o frontend passa esse valor como `currentOpeningOverride` pro modal, e quando o campo não muda, reenvia `currentOpeningOverride` (preserva o que já estava, seja automático ou explícito) em vez de sempre `null`. Só manda um valor **novo** quando o campo realmente é editado.
- **Saque/Depósito entre casa e "conta"** (`POST /bets/months/{monthId}/houses/{houseId}/transfer`, `BetService.transferBetweenHouses()`): move dinheiro entre uma casa e **outra casa qualquer, escolhida pela pessoa** sem contar como resultado de aposta. `TransferRequest(amount, type: "SAQUE"|"DEPOSITO", counterpartHouseId, date opcional)`. **Já foi fixo por nome "Banco"** (busca case-insensitive) — trocado pra um `counterpartHouseId` explícito porque tem gente com mais de uma conta/banco (ex: BTG e Mercado Pago na mesma conta) e precisava escolher qual. Valida que `counterpartHouseId` é uma casa diferente da casa de origem/destino (`400` se igual). Reaproveita `resolveEditableDate()` (extraído de `updateHouseBalance()`) pra validar a data. **Ajuste é sempre simétrico**: desloca `opening_balance` **e** o saldo final do dia (via `bet_daily_balances`) pelo mesmo delta, dos dois lados (casa e conta) — não só o saldo inicial como a descrição original do pedido sugeria. Se só o saldo inicial fosse ajustado, o saldo final (ainda não reeditado) ficaria "descasado" do novo inicial e geraria um resultado fantasma (positivo/negativo) até a próxima atualização manual daquele dia; a versão simétrica garante resultado zero pra ambas as pontas imediatamente, e já foi validada como correta e independente de ordem (fazer um saque antes ou depois de registrar o resultado real do dia dá o mesmo número final).
- **Agrupamento de casas** (`bet_house_groups`, `bet_houses.group_id` nullable, migration V12): permite juntar várias casas (ex: sub-contas de uma casa mãe, como "BTG - 365" e "Carro - 365" que na real são divisões do saldo de uma única conta Bet365) num grupo, pra ver o resultado **combinado** do grupo no dia e no mês, sem perder o resultado individual de cada casa. CRUD simples em `BetHouseGroupController` (`GET/POST /bets/groups`, `DELETE /bets/groups/{id}` — excluir o grupo só desvincula as casas, `ON DELETE SET NULL`, nunca apaga casa) e `PUT /bets/houses/{id}/group` (`AssignHouseGroupRequest.groupId` nulo remove do grupo). `computeMonthDays()` acumula os subtotais de grupo **no mesmo loop** que já soma por casa (nada de query extra): por dia, um `Map<groupId, [closing, opening]>` vira `BetMonthDayResponse.groups`; pro mês inteiro, um `Map<groupId, BigDecimal>` (mesmo padrão do `houseTotalResult`) vira `BetMonthDaysResponse.groupSummaries`. Cada casa também carrega seu `groupId`/`groupName` (resolvido via `h.getGroup()`, que é lazy — só usa `.getId()` direto no proxy, nunca `.getName()` sem passar por um `Map<UUID,String>` pré-carregado numa query só, pra não cair em `LazyInitializationException` fora de transação nem N+1). **Cuidado**: `computeMonthDays()` agora acessa `h.getGroup()` pra cada casa, então qualquer método que chame ele (direta ou indiretamente via `toSummary`) precisa de `@Transactional` — `startMonth()` e `transferWithBank()` ganharam a anotação por causa disso (ver seção "Cuidado com `open-in-view: false`" abaixo).
- **`DELETE /bets/months/{id}`**: exclusão simples — o cascade do banco (`ON DELETE CASCADE` em `bet_daily_balances`, `bet_unit_value_changes` e `bet_month_starting_balances`) já limpa tudo que pertencia àquele mês. Como o resumo de cada mês agora é sempre recalculado (ver acima), excluir um mês **não** deixa nenhum outro com número errado, nem o mais antigo nem o mais recente.
- **`BetService`** concentra toda a lógica (casas + mês + saldos) num service só, diferente do Financeiro que separa em vários — o domínio é pequeno o suficiente pra não precisar dividir.
- **Competição** (`bet_competitions`/`bet_competition_members`, migration V14, `BetCompetitionService` — service **separado** do `BetService`, esse aqui só compara pessoas diferentes, não mexe em casa/saldo): uma pessoa cria uma competição pra um **mês/ano específico** (não "o mês aberto dela" — um valor fixo, independente de qual mês cada participante tem aberto) e vira automaticamente o primeiro membro; isso gera um `code` (6 caracteres, alfabeto sem `O/0/I/1` pra evitar confusão ao digitar, `SecureRandom` com checagem de unicidade em loop). Qualquer outra pessoa entra via `POST /bets/competitions/join` com o código (case-insensitive, normalizado pra maiúsculas). **Só o resultado geral** (não por casa): `ranking()` pega cada membro, chama `BetService.summaryForUserAndPeriod(userId, year, month)` (método público novo, wrapper de `toSummary()` que busca o `BetMonth` do usuário por `year`/`month` exatos via `BetMonthRepository.findByUserIdAndStartDate` — reaproveita o **mesmo** `computeMonthDays()` de sempre, sem nenhuma lógica de agregação nova) e ordena por `profitLossUnits` desc — quem nunca teve um mês nesse período aparece com `hasData=false` e 0, não desaparece do ranking nem quebra. **Segurança**: ver a competição (`GET /bets/competitions/{id}/ranking`) exige ser membro (`existsByCompetitionIdAndUserId`), senão `404` (mesma mensagem de "não existe", pra não vazar que a competição existe mas a pessoa não faz parte) — isso é o único lugar do sistema onde um usuário vê o resultado (unidades) de outra pessoa, então o acesso é sempre por membership, nunca por dono/criador.

### Cuidado com empates em `ORDER BY` de datas

Esse módulo já pegou o mesmo bug duas vezes: qualquer `ORDER BY` numa coluna de data (`date`, `start_date`) sem desempate quebra quando dois registros caem no mesmo dia — e isso acontece na prática (corrigir um valor errado e reiniciar o mês/trocar a unidade de novo no mesmo dia é um fluxo real, não só de teste). Por isso:
- `bet_unit_value_changes` e `bet_months` têm uma coluna `created_at` (timestamp, não date) só pra desempate — toda query de "o mais recente" usa `OrderBy..DescCreatedAtDesc`, nunca só `OrderByDateDesc`/`OrderByStartDateDesc`.
- Se adicionar uma nova tabela/query nesse módulo que dependa de "qual registro é mais recente" baseado numa coluna `DATE` (não `TIMESTAMP`), adiciona `created_at` nela também desde o início.

## Onde entra o donut/gráfico de pizza do frontend

`GET /dashboard/visao-geral` retorna `abas: TabSummary[]` com `totalGastoPeriodo` de cada aba — é isso que dimensiona as fatias do gráfico de rosca na tela inicial do `financeiro-web` (`DonutTabChart.tsx`). Se mudar o formato desse campo, o frontend quebra o cálculo de proporção.

## A lógica mais importante do sistema: período fiscal

Está isolada em `util/FiscalPeriodCalculator.java`. Não é o mês de calendário — é uma janela custom que vai de `(closingDay + 1)` de um mês até `closingDay` do mês seguinte. Antes de mexer nisso, ler os comentários da classe com atenção; tem tratamento de meses com menos dias (clamp) que é fácil de quebrar.

## Estrutura de pacotes

```
com.financeiro.api/
  config/          # SecurityConfig (JWT, CORS)
  security/        # JwtService, JwtAuthenticationFilter, CurrentUser (helper pra pegar userId do contexto)
  entity/          # JPA entities
  repository/      # Spring Data JPA repositories
  dto/              # records de request/response, um subpacote por domínio
  service/         # lógica de negócio
  controller/      # REST endpoints
  util/            # FiscalPeriodCalculator
  exception/       # AppException + GlobalExceptionHandler (RestControllerAdvice)
```

Padrão seguido em todo módulo: `Controller` fino → `Service` com a lógica → `Repository`. DTOs são `record`s do Java, validados com Bean Validation (`jakarta.validation`).

## Cuidado com `open-in-view: false` + associações lazy

`open-in-view` está desligado (`application.yml`) — de propósito, é a prática recomendada. Isso significa que a sessão do Hibernate fecha assim que o repository retorna, então **qualquer método de Service que acesse uma associação `@ManyToOne`/`@OneToMany` lazy depois da query precisa de `@Transactional(readOnly = true)`** (mantém a sessão aberta até o fim do método). Já apanhamos com isso: `DashboardService.gastos()`/`devedores()` (acessava `expense.getCategory().getName()` e `debt.getDebtor().getName()`), `DebtorService.list()`/`detail()` (acessava `debtor.getDebts()`) e `ExpenseService.list()` estavam sem a anotação e estouravam `LazyInitializationException` (500) assim que havia dado real — o dashboard vazio nunca pegava esse bug, só apareceu ao testar com um gasto/dívida de verdade. Se criar um novo método de leitura que atravesse uma associação lazy, adiciona `@Transactional(readOnly = true)` nele também.
